01 · Where things are shown

Three layers, each with one job

Gateway keys, provider APIs and uploads each get an overview, but that overview is about the source itself: is it connected, fresh and complete? Spend by team, by model or by person never appears on a source page. That belongs to analysis, which always works from the combined, de-duplicated data, never from one source alone.

Data SourcesCan I trust the input?
  • Connected / failing / stale
  • Records per day, last sync
  • Coverage: % of the invoice it sees
  • Raw records, exactly as received
Never: spend by team or model
→
Truth layer (no tab)One cost line per day × owner × meter
  • De-duplicated across sources
  • Owner assigned by rule
  • Evidence grade attached
  • Priced at the client's real rates
This is a backend job, not a screen.
→
Analysis & actionWhat does the money mean, and what do we do?
  • Cost Explorer, Invoice Reconciliation, Recommendations
  • Budgets, Reports, Team Home
  • Always the combined truth
Never: a raw table from one source

One small link between them: Overview and the status bar show a single data-health line ("10 of 12 sources healthy, 96% of the bill reconciled") that links to Data Sources. It's like a fuel gauge on a dashboard: you see it, but the engine lives elsewhere.

02 · The structure

Every tab and sub-tab

Organised by what people come to do, not by data source. Click a page to see its sub-tabs, what each shows, and what's deliberately not there. Badges show what exists today in some form (exists), what is a rework of something existing (rework) and what is new (new).

Rules from the AWS Cloudscape guidelines: group by the user's tasks, keep groups few, never a group of two, and exactly one active link. Admin pages sit at the bottom, apart from daily work. One scope bar (organisation › team › project, plus period) drives every page; a page has sub-tabs, and a sub-tab never has its own tabs.

Why four tabs. Each tab answers one question. Overview: can the data be trusted? It shows source health, invoice coverage and the issues to fix. Data quality lives here because it answers the same question. Accounts: what is connected? Providers, AI tools, agent platforms, cloud billing exports and custom sources share one list with a category filter, and each row opens its raw records and sync history. Gateway: what passes through Token IQ? Traffic, request log, virtual keys and upstreams. Uploads: what arrives as files? The separate Ingest API tab is gone, because your own applications connect as a Custom source that sends usage, and that creates the ingest token for them.

Design system

Built on what you have

React + Tailwind + shadcn/ui stay. Add TanStack Table for every table, cmdk for the command palette, and one chart library used everywhere. Put the page templates in ui/src/components/shell/ so a new page is assembled, not designed.

Type and spacing

One type scale (12 · 13 · 14 · 16 · 20 · 24), a 4-pixel spacing grid, two densities (comfortable, compact), tabular figures for every number.

Colour with meaning

One brand colour for actions and selection. Green, amber and red only for state (healthy, attention, failing). Evidence grades always in the same three colours. Light and dark themes from the same tokens.

Words

Money first, tokens second. Every number has a comparison. Plain labels ("Spend with no owner", not "Nobody owns"). Empty states say what will appear and how to make it appear.

04 · Roles and access control

Eight roles, each limited to what it needs

Access has two parts: the role decides which pages and actions a person has; the scope (organisation, one team, or only themselves) decides which data they see. Scope is enforced in every page, tab, export, scheduled report, assistant answer, API call and MCP query, and in the status bar. Try each role with "View as" in the mockup above.

Org Owner

Accountable for Token IQ

Everything an Org Admin can do, plus the licence and ownership transfer. One or two people; cannot be removed by an admin. Password sign-in is kept only for this role as a break-glass option.

Org Admin

Runs the platform

Manages: Data Sources, Organization, Access Control, Cost Allocation, Pricing, Integrations, Settings, all virtual keys and governance. Grants every role, including both Team Lead roles.

Sees: all data.

Finance Admin

Owns cost

Manages: Invoice Reconciliation and month-end close, budgets and approvals, Contracts & Licenses, Cost Allocation, Pricing & Rates, reports. Uploads invoices.

Sees: all cost data; Data Sources, Organization and Access Control read-only. No settings.

Org Viewer

Read-only, organisation-wide

For executives and auditors. Sees all analytics, optimization and governance pages, and Access Control read-only (who has access, and the audit log); can export. Changes nothing.

Team Lead (Manage)

Runs one team

Sees only their team, starting from Team Home. Manages members' limits and allowed models, approves member requests, adds employees to the team as Team Members, creates projects and virtual keys, assigns recommendations, sets team alerts and reports, and requests budget changes.

Team Lead (Read-only)

Views one team

Same pages and same team data as Team Lead (Manage), with every button that changes something removed. For deputies, project managers and engineering managers who need visibility without control. Can export team reports.

Team Member

Read-only, own usage

Sees only their own usage: cost, tools, keys and seats, and the limit and models their Team Lead set. Cannot change anything; asks their Team Lead for keys, models or a higher limit.

Service Account

Non-human access

For BI exports, ingestion and MCP assistants. Has one purpose (read, ingest or MCP), a scope and an expiry date. Never uses a person's credentials.

Naming in the product

Standard terms

Page names follow cloud-console and FinOps Foundation vocabulary (Cost Explorer, Budgets & Forecasts, Anomalies, Recommendations, Chargeback), so finance and engineering teams recognise them immediately.

Title plus description

Every page has a one-line description directly under its title; every tab has one under the tab bar.

Actions as verbs

Buttons name the action: "Create budget", "Invite user", "Upload invoice", "Connect account". Never "Submit" or "OK".

Consistent terms

One term per concept everywhere: virtual key, allocation rule, effective rate, unallocated cost, realized savings. The glossary defines each.

06 · Connecting accounts

One place to connect, two kinds of credential

Billing access (what Token IQ reads) and forwarding access (what the gateway sends traffic with) are different jobs with different risks. Today both live on "LLM Provider Credentials"; they move to separate screens.

Billing access · read-only

Every provider, AI tool, agent platform, cloud export and custom source. One dialog: what you are connecting → how you use it → connect → permission check → owner and history. Also reached from the Overview setup checklist, the Overview issues list and any empty analysis page.

Rules behind the wizard

Sign in wherever the provider allows it

Microsoft (Azure, Microsoft 365 Copilot, Entra ID in one consent), Google (Vertex AI) and GitHub (Copilot) each get a sign-in button. No secret is copied, stored or rotated, and the client can revoke access from their own admin centre.

A guided key where it doesn't

OpenAI and Anthropic have no sign-in for reading an organisation's billing, so they get three guided steps: open the exact admin-keys page in a new tab, create a key with a suggested name, then paste it in and see a live check that names the organisation and what can be read. It should feel almost as quick as signing in.

Recommend the safest method first

Sign-in or a cloud role first (no secret stored), a guided key second, files last. Mark the recommended one, and put options like AWS access keys behind a second tab marked "not recommended".

Check before saving

Your code already rejects ordinary keys for OpenAI and Anthropic by prefix (sk-admin-, sk-ant-admin). Extend that into a live permission check per endpoint, so a key never saves and then fails every sync.

Never show a secret again

After saving, show only the last 4 characters, who added it and when. Replacing a key is a new entry; the old one is kept in the audit log, not in plain text.

Store secrets in a secrets manager

Use the deployment's secrets manager rather than the database: AWS Secrets Manager on the ECS set-up chosen on 30 September (per docs/status.md, today PROJECT.md), or Azure Key Vault for a client that hosts on Azure.

Say what this plan can't give

The last step lists what will and won't be visible with this plan and method, and the same note stays on the account's page.

Owner and backfill at connect time

Ask for a default owning team and how many months to load. A new account then shows history and attribution from day one.

07 · Recommendations engine

Make recommendations the reason people open Token IQ

Today there are four rules, and two of them carry no figure. A recommendation people trust has to do five things, and almost no tool does all five. Most stop at the first step.

1 · FIND

Detect a pattern

Rules run nightly over cost lines, gateway metadata, seats and tool usage. No prompts needed.

2 · SIZE

Price it on real traffic

Re-price the matching requests under the change, at the client's effective rates (invoice ÷ list price), not list prices. Give a range, not a single point.

3 · PROVE

Show the evidence

Matching requests, the date range, sample request IDs and the assumptions made. For model swaps, an optional quality check on a sample.

4 · HAND OVER

Make it easy to act

An owner, a ready-to-use change (a config snippet, a gateway policy for their own setup, a ticket). Token IQ itself never changes traffic.

5 · VERIFY

Measure the real saving

After it's marked done, compare before and after on the same traffic. The saving moves from "estimated" to "verified".

08 · Your idea: the gateway in reverse

A shadow gateway: run every routing policy as a simulation, never on live traffic

Your instinct is right, and it fits the product unusually well. Gateways like LiteLLM and Bifrost apply routing, caching and fallbacks live, which is exactly what Kore.ai doesn't want: their requirement is a proxy that never changes a request. Token IQ can run the same logic as a dry run over observed traffic and report what each policy would have saved, without touching a single call. The client keeps full control and gets the numbers to decide.

You already have the code.

project_usage/ in the fork records that weighted/cost-based routing (01), load balancing (02), fallbacks (03), rerouting retries (04) and response caching (05) were removed or neutralised in the live path, with notes on how to restore each. Restore them inside a sandboxed "simulator" module that reads gateway records and never sees a live request. The router code, prompt_caching_cache.py, the complexity-router config and batch_utils.py are all there to reuse.

Live gateway feature (LiteLLM / Bifrost)Token IQ turns it into…What the simulation needs
Cost-based / complexity routing"Model fit": which requests a cheaper model could serve, and the savingToken counts, call shape, the complexity-router rules (already in the fork)
Load balancing across deployments"Provider arbitrage": the same model is cheaper on another account you already own (Claude on Bedrock vs Anthropic; GPT on Azure vs OpenAI)Effective rates per account from invoices
Response caching"Duplicate requests": identical requests answered fresh every timeA one-way hash of each request computed in flight. The prompt itself is never stored.
Prompt caching"Cache opportunity": long repeated prefixes (system prompts, tool definitions) not using provider cachingHash of the first N tokens, plus cached-token fields from provider usage
Batching"Batch-eligible": non-interactive traffic (nightly jobs, back-office keys) eligible for the batch discountTime-of-day pattern, key purpose, latency tolerance
Fallbacks & retries"Failure cost": spend on failed and retried calls, and the reliability gain from a fallbackStatus codes, retry chains per session

The hashing approach keeps the observer-only promise and privacy intact: Token IQ learns that two requests were identical, or shared a 3,000-token prefix, without ever storing either one. Simulations based on metadata cover pricing levers. Only model-swap rules need a quality check, and that runs on a sample the client approves.

12 · Badly missing

What to add, in order of importance

Must

Pricing & Rates: effective rates

Contracted rates, discounts, PTU commitments and exchange rates (USD → INR, GST). Every simulation and recommendation needs the client's real prices, not list prices. Derive an effective rate per account as invoice ÷ list-priced usage. List prices come from Token IQ's own price file with dated history, so any past period re-prices at the prices of that time (section 11).

Must

Identity mapping

Directory sync (Entra ID / Okta) so one person is one identity across gateway keys, ChatGPT, Claude Code and Copilot. Without it there's no per-person view and no seat recommendations.

Must

Request fingerprints at the gateway

A hash of the whole request and of the first N tokens, computed in flight and stored without content. This unlocks the duplicate-request, cache-opportunity and runaway-loop rules while keeping the privacy promise.

Must

Realized Savings ledger

Every recommendation marked done is re-measured after 14 and 30 days. It's the proof of value for the client and for NITCO.

Must

Guidance layer and setup dialogs

Page guide and Ask Token IQ on every page, a two-tab setup dialog (Setup guide, Configure) for every setup button, the Overview setup checklist and Documentation.

Eight roles (Org Owner, Org Admin, Finance Admin, Org Viewer, Team Lead (Manage), Team Lead (Read-only), Team Member, Service Account), SSO, audit log, team activity, member limits, and team scope enforced in pages, exports, reports, the assistant, the API and MCP.

App shell and page templates

The top bar with scope picker and search, the new left nav, and the five templates (overview, explorer, table view, detail page, setup dialog). Every later page is then quick to build and consistent.
